# 커밋 컨벤션

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/) 을 따릅니다.

## 형식

```
<type>[(scope)][!]: <설명>

[본문]

[꼬리말]
```

- 제목, 본문, 꼬리말은 **빈 줄**로 구분합니다.
- 본문과 꼬리말은 선택입니다.

## 제목 규칙

| 항목 | 규칙 |
|------|------|
| type | 영문 소문자, 아래 표에서 선택 |
| scope | 선택. 영역을 나타내는 명사를 괄호로 감쌈. 아래 scope 목록 사용 |
| `!` | 하위 호환을 깨는 변경이면 `:` 바로 앞에 붙임 |
| 설명 | 한국어, 무엇을 했는지 간결하게. 명사형 또는 `~추가`, `~수정`처럼 끝맺음. **마침표 금지** |
| 길이 | 제목 전체 50자 내외 (최대 72자) |

## type

| type | 용도 | SemVer |
|------|------|--------|
| `feat` | 새 기능 | MINOR |
| `fix` | 버그 수정 | PATCH |
| `docs` | 문서만 변경 | - |
| `style` | 동작에 영향 없는 포맷·공백·세미콜론 수정 | - |
| `refactor` | 기능 변화 없는 구조 개선 | - |
| `perf` | 성능 개선 | - |
| `test` | 테스트 추가·수정 | - |
| `build` | 빌드·의존성 변경 (`requirements.txt` 등) | - |
| `ci` | CI 설정 변경 | - |
| `chore` | 그 밖의 잡무 (`.gitignore` 등) | - |

`BREAKING CHANGE` 가 있으면 어떤 type 이든 **MAJOR** 입니다.

## scope 목록

작업 이슈와 맞춥니다. 해당 없으면 생략합니다.

| scope | 영역 | 이슈 |
|-------|------|------|
| `setup` | 환경 변수, LLM 초기화, 입력 데이터 | #1 |
| `translate` | 번역·요약 체인 | #2 |
| `urgency` | 긴급도 평가·언어 식별 체인 | #3 |
| `reply` | 답변 생성·답변 번역 체인 | #4 |
| `chain` | 전체 체인 결합 | #5 |
| `run` | 실행 및 결과 출력 | #6 |

## 본문

- 무엇을, **왜** 바꿨는지 적습니다. (어떻게는 코드가 설명)
- 제목과 한 줄 띄우고 작성, 한 줄은 72자 내외로 줄바꿈합니다.

## 꼬리말

Git trailer 형식(`토큰: 값`)을 씁니다. 토큰의 공백은 `-` 로 대체합니다.

| 꼬리말 | 용도 |
|--------|------|
| `Closes #N` | 이 커밋/PR이 이슈 N을 완료함 (병합 시 이슈 자동 종료) |
| `Refs: #N` | 이슈 N과 관련은 있으나 완료는 아님 |
| `BREAKING CHANGE: <설명>` | 하위 호환 깨짐. **반드시 대문자** |
| `Co-Authored-By: 이름 <이메일>` | 공동 작업자 |

## 예시

좋은 예

```
feat(translate): 문의 이메일 번역 체인 구현
```

```
feat(chain): RunnablePassthrough.assign 으로 4단계 체인 결합

요약, 긴급도, 언어 식별은 서로 독립이므로 2단계에서 한 번에 assign 한다.
언어 식별은 번역본이 아닌 원본(inquiry)을 입력으로 사용한다.

Closes #5
```

```
fix(urgency): 긴급도 프롬프트가 숫자 외 문장을 반환하는 문제 수정

Refs: #3
```

```
refactor(chain)!: 체인 결과 키 urgency_score 를 urgency 로 변경

BREAKING CHANGE: combined_chain 결과 딕셔너리의 urgency_score 키가 urgency 로 바뀐다.
```

```
chore: .gitignore, 의존성 목록, 환경 변수 예시 추가
```

나쁜 예

| 메시지 | 문제 |
|--------|------|
| `update code` | type 없음, 내용 불명 |
| `Feat: 번역 체인.` | type 대문자, 마침표 |
| `feat(번역): 체인 추가` | scope 가 목록 밖(한글) |
| `fix: 여러 가지 수정` | 변경 내용 모호 |
| `feat: 번역 체인 구현, 요약 체인 구현, README 수정` | 서로 다른 작업을 한 커밋에 섞음 |

## 커밋 전 체크리스트

- [ ] type 이 표에 있는 값인가?
- [ ] scope 가 목록에 있거나 생략되었는가?
- [ ] 제목이 50자 내외이고 마침표가 없는가?
- [ ] 한 커밋에 하나의 논리적 변경만 담았는가?
- [ ] 이슈 완료 시 `Closes #N`, 관련만 있으면 `Refs: #N` 를 달았는가?
- [ ] `.env` 나 API 키가 포함되지 않았는가?

## Claude 가 커밋 메시지를 쓸 때

1. `git diff --staged` 로 변경 내용을 확인하고, 여러 논리 단위가 섞였으면 나눠 커밋하자고 제안합니다.
2. 위 규칙에 맞는 메시지를 작성합니다. 브랜치 이름(`<type>/<이슈번호>-...`)에서 type 과 이슈 번호를 참고합니다.
3. 규칙에 어긋나는 메시지는 어떤 항목이 틀렸는지 짚고 고친 안을 제시합니다.
